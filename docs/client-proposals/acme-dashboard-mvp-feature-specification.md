# Acme analytics dashboard MVP — feature specification candidate

**Status:** Proposed discovery artifact, not Acme-approved scope. **Issue:** [#22](https://github.com/Ryner88/project-command-center/issues/22). **Updated:** October 23, 2026.

## Authority and product boundary

The [recovered proposal](analytics-dashboard-mvp.redacted.pdf) offers Acme an executive web analytics dashboard with real-time reporting and AI-assisted weekly summaries. It commits to no named pages, charts, KPI formulas, filters, or permission model. The [source audit](analytics-dashboard-mvp-requirements-audit.md) records these gaps. The proposal's four phases are Discovery and planning, Execution and reviews, QA and final revisions, and Handoff and closeout. Their dates are not redefined here.

Sarah Chen and Apex Retail Co. are fictional **agency proposal** fixtures. Their status, price, and client fields can test a candidate reporting pattern. They do not establish Acme's business metrics, data sources, users, or approval. Project Command Center's proposal dashboard is an internal application, not a client deliverable. The [agency application scope](../proposal-mvp-feature-scope.md) remains separate.

## Simulated agency proposal scenario — specification test only

Use the two local PDF exports identified in the [reporting specification](acme-dashboard-reporting-specification.md) to evaluate whether the candidate requirement format is sufficiently precise. A simulated proposal overview would show total proposals, status counts (Draft, In Review, Sent, Won, Lost), estimated pipeline value as a **range**, and a client/project list. A simulated list would support client, project, status, and date-range filters with visible active filters and a reset. A simulated detail view would show the selected proposal and its source date and price range. These are **Project Command Center test behaviors**, not Acme dashboard features. No chart type is assumed from the two PDFs.

| Fixture check         | Simulated acceptance condition                                                                                                                                                   | Evidence needed                                                              |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Status                | Assign Sarah `DRAFT` and Apex `SENT` in a separate test dataset; counts read Draft 1, Sent 1, all other statuses 0. Change a status and verify exactly one count moves.          | Saved test records and status history, not the PDFs                          |
| Client/project filter | Exact client or project selection returns the matching fixture; clearing both returns two. Combined filters use intersection, with a useful zero-result state.                   | Saved test records and filter result                                         |
| KPI consistency       | Overview total equals the count of filtered rows, and status counts sum to that total. Estimate ranges follow the reporting formula; no single exact contract value is asserted. | [Metric contract](acme-dashboard-reporting-specification.md) and test output |
| Approval record       | A simulated decision records its proposer, source, reviewer, explicit approval state, version, and date. A pending or simulated entry cannot be rendered as Acme approval.       | Fixture decision log, separate from the Acme approval record                 |

The PDFs do not contain status, creation/update timestamps, record IDs, or approval events. Those fields must be supplied by labeled simulated records before the corresponding tests can run. Do not import PDF text as production application data or upload unredacted exports to the public repository.
