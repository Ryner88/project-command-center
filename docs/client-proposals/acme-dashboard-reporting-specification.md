# Acme analytics dashboard — reporting contract candidate

**Status:** Proposed discovery artifact and simulation contract, not Acme-approved reporting requirements. **Issue:** [#23](https://github.com/Ryner88/project-command-center/issues/23). **Updated:** October 23, 2026.

## Source and missing contract

The [recovered proposal](analytics-dashboard-mvp.redacted.pdf) promises real-time reporting for an executive analytics dashboard and assumes needed systems and APIs will be available for testing. It names no source system, KPI, refresh interval, latency target, data volume, ingestion method, failure policy, or integration owner. The [requirements audit](analytics-dashboard-mvp-requirements-audit.md) and [discovery worksheet](acme-dashboard-discovery-worksheet.md) capture the unresolved decisions. Agency proposal records and PDFs are **not** Acme's analytics feed.

## Acme metric, source, and timing contract to complete

The [simulated stakeholder review](acme-simulated-review-v0.1.md) requested changes to every reporting area. The following fields make those objections testable without assigning fictional values to Acme. Enter the approved answers and evidence in the [single approval package](acme-requirements-approval-package.md); keep this specification **Candidate — Pending Client Approval** until then.

| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| KPI catalog             | For each KPI: business question, formula including numerator/denominator where applicable, unit/currency, rounding, reporting period, event-date basis/timezone, permitted dimensions, missing/duplicate/zero-denominator policy, and reference rows with expected result. | Recompute the KPI independently from the signed reference rows; compare displayed value, unit, period, and breakdowns.                                                           |

| Refresh and latency     | Approved dashboard refresh method/interval `[R]`; maximum event-to-visible age `[L]` at percentile `[P]` over observation window `[W]`; clock synchronization and measurement method.                                                                                      | Timestamp source events and browser-visible values; calculate age for all sampled updates and verify the approved percentile is at most `[L]` during `[W]` at the approved load. |

`[R]`, `[L]`, `[P]`, `[W]`, and `[S]` are unfilled approval fields, **not proposed targets**. The source proposal supplies none of their values. A test cannot pass by substituting an arbitrary number or the internal application's page-load behavior. No Acme KPI or source system is named in the source proposal; the proposal-pipeline formulas below remain simulation-only examples.

## Candidate metric definitions for the simulation

These definitions use a hypothetical snapshot of active, owner-visible Project Command Center proposal records. They are **not** approved Acme KPIs. All metrics must use the same filtered record set and snapshot time. Archived records are excluded. A proposal is counted once by stable ID. A PDF file alone is never counted as a live record.

| Metric                    | Candidate formula                                                                                                                                                        | Presentation and edge cases                                                                                                                                                                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Total proposals           | Count distinct selected proposal IDs.                                                                                                                                    | Integer; zero is shown explicitly.                                                                                                                                                                                                                                                                                                            |
| Status breakdown          | Count selected IDs for each of `DRAFT`, `IN_REVIEW`, `SENT`, `WON`, `LOST`; `Won/Lost` summary is `WON + LOST`.                                                          | Five counts sum to total. Preserve separate Won and Lost counts even if a compact card combines them.                                                                                                                                                                                                                                         |
| Estimated pipeline range  | Sum the parsed lower bounds and sum the parsed upper bounds separately for selected **open** statuses (`DRAFT`, `IN_REVIEW`, `SENT`); present the two totals as a range. | Show `$lower–$upper` and label as estimates, not booked revenue. Exclude Won/Lost from open pipeline. Never add range strings or silently use their midpoint. Invalid/missing ranges are counted as unpriced and excluded from both sums, with a visible warning. Currency conversion and mixed-currency treatment need an explicit decision. |
| Client-specific reporting | Apply an exact client ID or normalized client key to the selected records before all aggregates.                                                                         | A display name alone may collide; require a stable key in the real source contract. A PDF name is sufficient only for this two-record simulation.                                                                                                                                                                                             |
| Date-range reporting      | Proposed simulation uses proposal **creation time** in UTC, start inclusive and end exclusive.                                                                           | Display selected timezone and range. The PDFs have delivery start/due dates, not creation time; date-filter tests require separate simulated creation timestamps. Acme must choose its own event date and timezone.                                                                                                                           |

For a simulated snapshot with Sarah `DRAFT` and Apex `SENT`, both active and both in range, total is **2**, status counts are Draft **1**, Sent **1**, other statuses **0**, and open estimated pipeline is **$18,000–$28,000**. Filtering to either client yields **1** and **$9,000–$14,000**. Moving Apex to `WON` leaves total **2**, makes Won **1** and Sent **0**, and lowers open pipeline to **$9,000–$14,000**. These are arithmetic examples, not measured live application results or Acme targets.

## Candidate data-source and refresh model

| Reporting path               | Data source and ownership                                                                                                                      | Refresh and failure behavior                                                                                                                                                                                                | Approval state         |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| Simulated internal proposals | Saved Project Command Center PostgreSQL proposal records, scoped to current owner; PDFs supply static field examples only.                     | A fresh server read on page load or after a saved mutation is a possible test model; show snapshot time. No automatic polling or latency guarantee follows from that behavior.                                              | Simulation only        |
| Acme executive analytics     | Named Acme systems, APIs, credentials, source owners, event clocks, ingestion jobs, transformations, and reconciliation owner are **pending**. | Publishing cadence, fetch/push method, maximum event-to-visible delay, percentile, observation period, expected/peak volumes, backfill, retry, stale threshold, outage state, recovery, and reconciliation are **pending**. | Acme approval required |

For Acme, define freshness as `dashboard visible time − source event time` and separately define `source publication time − source event time`, so source delay is not hidden in an application-only timer. Specify clock synchronization, sampling method, percentile, and observation window. Each source should display last successful ingestion and its health state; the exact stale threshold and whether old values remain visible require approval. No numeric value is proposed here because the source provides none.

## Approval and exit gate

The authorized Acme reviewer must approve named systems, source owners, ingestion method, authentication/access ownership, volume and backfill bounds, each KPI formula and dimensions, refresh and end-to-end latency thresholds, stale/outage/recovery/reconciliation behavior, and expected outputs for R06–R07 and R11–R12. Record evidence, approver, date, and scope version in the [approval package](acme-requirements-approval-package.md), then expressly incorporate the contract into the client agreement. Keep #23 open until those decisions and passing acceptance evidence exist. R01–R05 and R08–R10 are proposed simulation tests; they cannot establish Acme's reporting promise. No Acme analytics implementation exists in this repository, so none of R06–R07 or R11–R12 has been executed.
